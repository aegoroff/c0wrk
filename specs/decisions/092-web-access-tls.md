# ADR-092: TLS for the web-access sidecar

## Status

Accepted → Closes the deferred half of [ADR-090](./090-browser-web-access.md) decision 3 ("Transport security (TLS) is out of scope and gets its own future decision") → Amends the "plain HTTP stays the only transport" invariant and the cookie-`Secure` known limitation of [domains/web-access.md](../domains/web-access.md) → Extends ADR-090 decision 12's warn-only exposure model with an encryption stage; the exposure classification and every existing warning stand unchanged

## Context

The web-access sidecar serves the desktop UI to a browser over plain HTTP: the session cookie omits `Secure` (recorded in code and in the domain spec as a known limitation "a TLS stage must flip it on"), and on a non-loopback bind the auth token is the *only* protection — traffic, including the login POST body, travels unencrypted. ADR-090 rejected shipping TLS together with the sidecar (certificate provisioning is a scope of its own) and explicitly left the seam open: bind address and credential handling had already arrived as mounted parameters, TLS termination was "the remaining seam".

Three forces shape the decision now. First, the operator need is real and bounded: serve `https://` from the sidecar without external tooling (no reverse proxy, no ACME client) — a self-signed certificate generated for the *currently pinned bind* covers the loopback and LAN-IP cases, and an operator holding a real certificate (or a proxy front) can point the config at it by hand. Second, the fail-soft/fail-closed doctrine of the config section gives an exact template for "TLS configured but broken": structural invalidity (TLS enabled with empty paths) follows the load-time fail-soft reset precedent, while a configured-but-unreadable pair must never silently downgrade the listener to plaintext — the existing mount is already fail-soft-and-loud on start failures, which *is* fail-closed for free. Third, the UX budget of the Settings block is already at its comfortable ceiling (one toggle, one URL field, one token field): the protocol must be a separate explicit switch, not a scheme parsed out of the address field, and the certificate needs one path field plus one generate button — no more.

## Decision

The sidecar gains optional TLS termination, and the certificate it serves is generated by the app itself for the pinned bind:

1. **The protocol is its own switch: a `web_access.tls` subsection, externally toggled — never parsed out of the address field.** `tls.enabled` (default false) turns TLS on; `tls.cert`/`tls.key` carry PEM paths. The Settings address field keeps its host:port-only grammar (`https://` in the field is refused with a message pointing at the HTTPS toggle), and the toggle commits through its own control RPC `SetWebAccessTLS` on the desktop surface (ADR-090 decision 4) with the section's persist + hot-restart + rollback discipline. The rendered/copied browser URL switches to `https://` when TLS is on, so what the operator sees is always what the browser must open.

2. **Validity is layered exactly like the rest of the section; a broken TLS never downgrades to plaintext.** Structural invalidity (`tls.enabled` with empty cert/key paths) is fail-soft at load — the TLS subsection resets to disabled with a visible warning and the sidecar serves HTTP, the same "broken section never keeps the app from starting" doctrine as the bind/port gate — and fail-closed at save. A *non-empty but unreadable* pair (missing file, parse error, key/cert mismatch) is fail-closed at mount: `New` refuses to construct the sidecar, the start fails loudly (Error log, error to the toggle caller, hot-restart rolls back to the previously persisted state), and the app continues desktop-side — a listener that serves plaintext when the operator configured encryption is never an outcome. The persisted switch stays on; the next launch retries.

3. **The generated certificate is app-owned and address-scoped: one fixed pair in `~/.c0wrk`, regenerated for the current bind.** The Generate control — the second new desktop RPC, `GenerateWebAccessCertificate` — writes `~/.c0wrk/web-access.crt` + `~/.c0wrk/web-access.key` (paths through the `backend/config` path API): a self-signed ECDSA P-256 leaf, ServerAuth, 825-day validity, atomic write, key 0600 / cert 0644, with SANs covering the *currently pinned* bind — `{localhost, 127.0.0.1, ::1}` always, plus the bind's browser-facing host (a wildcard bind names `localhost`, a specific IP names itself). Generation persists the pair's paths into the section (minting-is-part-of-configuring, the token precedent) and hot-restarts a running sidecar onto the fresh certificate; it never flips `tls.enabled` and never touches operator-authored paths — clicking Generate overwrites only the standard pair it owns.

4. **The single cert-path field stays single; the key is derived, the file stays the escape hatch.** The UI authors `tls.cert` only; an empty `tls.key` derives `<cert-stem>.key` at commit time. A non-standard layout (e.g. certbot's `fullchain.pem` + `privkey.pem`) is authored by editing `config.yaml` directly — the same hand-edit doctrine as static tokens, where tightening the UI must never lock an operator out of their own config.

5. **The cert/address mismatch is computed by the backend and surfaced as one warning.** `GetWebAccessInfo` gains additive fields (`tls_enabled`, `tls_cert`, `tls_key`, `cert_status`, `cert_detail`); whenever a cert path is configured, the leaf is read and checked against the pinned bind — SAN coverage of the browser-facing host, parseability, and expiry — producing `ok` / `mismatch` / `unreadable` / `expired`. The Settings block renders the detail as a warning row; changing the bind after the certificate was generated is the canonical mismatch trigger, and regenerating is the fix.

6. **TLS turns the documented limitations off, nothing else.** With TLS serving, the session cookie carries `Secure` (the KNOWN-LIMITATION comment's named resolution); on plain HTTP the cookie stays as today, so the HTTP behavior is byte-identical to pre-ADR. The same-origin WS check, the rate limiter, the denylist, the control-RPC placement (desktop.App only, ADR-090 decision 4) and every exposure warning are untouched; `MinVersion` is pinned to TLS 1.2.

## Consequences

Positive:

- The last ADR-090 stage seam closes: the sidecar now serves the same UI over an encrypted transport, and a non-loopback bind no longer means "token over plaintext". The loopback default keeps working exactly as before (TLS off = zero behavior change).
- The mismatch warning turns a previously silent breakage (cert generated for one address, bind later changed, browser hostname-verification failure with no hint why) into a visible, actionable row next to the control that fixes it.
- All new code sits in the existing seams — a `certgen.go` file in `internal/webaccess` (stdlib only, hygiene test untouched), one desktop file for the two control RPCs, additive config fields — so the removal path of the feature grows by deletion, not surgery.

Negative:

- A self-signed certificate still shows the browser's warning screen; the app does not touch the OS trust store (a deliberately rejected alternative — platform trust handling is a product decision of its own), so the operator accepts the warning once per browser or imports the cert manually.
- The sidecar can now be *down* where it previously would have been up-but-plaintext (TLS on, files broken): `running:false` with a loud error is the honest state, but an operator who ignored the Settings warning loses browser access at the next restart until they fix or disable TLS.
- The 825-day validity and the fixed file pair mean a long-lived install silently crosses the expiry at some point — the `expired` status exists precisely to make that visible instead of discovered through a browser error.
- The new `SetWebAccessTLS`/`GenerateWebAccessCertificate` control RPCs and the `GetWebAccessInfo` payload extend the wire surface; the Wails bindings regenerate and stale frontend fixtures need the additive-default treatment.

## Alternatives Considered

- **Scheme-in-the-address-field as the TLS switch** (`https://host:port` enables TLS) — rejected: the field already carries two values (host, port); a third overlapping the toggle's state invites divergence between what the field shows and what serves. The user chose the separate toggle.
- **Fail-soft HTTP fallback when the configured pair is unreadable** — rejected (user decision): it silently serves plaintext where the operator configured encryption, the exact "silently leaves an unsafe listener configured" outcome the section's doctrine forbids. A *structural* (empty-path) misconfiguration still fails soft, because there is no operator intent to betray — only a half-typed section.
- **Trust-store integration** (mkcert-style local CA install) — rejected for this stage: per-platform trust tooling (macOS keychain, Windows cert store, NSS DBs) is a scope of its own with its own security review; the self-signed warning is the documented accepted consequence.
- **Operator-typed arbitrary generation path** (Generate writes wherever the field points) — rejected: the button would become an arbitrary-file-writer keyed on a text field, and could overwrite an operator-provided certificate; the fixed app-owned pair is idempotent to regenerate and safe to click.
- **ACME/Let's Encrypt in the sidecar** — rejected: external network dependencies and renewal lifecycle are far beyond the local-sidecar scope; operators needing trusted certs keep the reverse-proxy route ADR-090 already documented.
- **RSA keys for maximum compatibility** — rejected: ECDSA P-256 is universally supported by every browser this feature can reach and halves the key-handling surface; RSA remains available to hand-configured certificates.
