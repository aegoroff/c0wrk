# ADR-091: The web-access sidecar mounts only behind the experimental gate

## Status

Accepted → Amends [ADR-090](./090-browser-web-access.md) (the availability model only — the sidecar architecture, its config section, its control RPCs and every other decision stand unchanged) → Records the first deliberate exception to [ADR-068](./068-embedded-llm-frontend-experimental-gate.md)'s frontend-only rule for experimental gates (the embedded-model gate stands unchanged) → Further ages the "the switch still gates only the E2S execution mode" wording in [ADR-044](./044-model-profiles-out-of-experimental.md) and [ADR-056](./056-research-always-on-global-seeding.md)

## Context

[ADR-090](./090-browser-web-access.md) shipped browser web access as an always-available opt-in: the feature's own `web_access.enabled` switch (default off) was its only gate, and the sidecar mounted at every launch whose config carried it. The surface is experimental-grade by any reading: a browser tab holds full control of the app by design (ADR-090 decision 2 — "accepted consequence, stated explicitly"), a non-loopback bind rides plain HTTP with the token as the only protection (decision 12), and the feature was still being amended in the field while shipping — decisions 8–12 (the HITL inbound whitelist, the boot barrier and pinned extra surface, the credential lifecycle, the web-mode adaptations, the warn-only exposure model) all landed as post-ship corrections. That is exactly the profile of surface the master experimental switch (`experimental.enabled`, all-or-nothing) exists to keep off every default machine while it stabilizes.

The gate's scope has a history: [ADR-044](./044-model-profiles-out-of-experimental.md) graduated Model Profiles out and left the switch "gating only the E2S execution mode"; [ADR-068](./068-embedded-llm-frontend-experimental-gate.md) added the embedded model's frontend surfaces and recorded a rule for how such gates work — hide the UI, never the capability, so no stored config can silently diverge from effective behavior. Web access fits neither half of that rule alone. A frontend-only gate would hide the Settings block while `web_access.enabled: true` kept mounting a full-remote-control listener at every startup — hiding the ONLY surface that shows the feature is on, which is the failure mode the rule exists to prevent. But web access also has what the embedded model never had: a running server whose lifecycle the app already hot-manages (the toggle's persist + start/stop discipline under `webAccessMu`), so the gate can follow the switch live and stop the listener for real — without touching anything persisted.

## Decision

Web access joins the experimental gate's scope, and the gate is a **conjunction enforced externally to the section**:

1. **Availability = `experimental.enabled && web_access.enabled`, evaluated where the sidecar mounts.** The startup mount (`initWebAccess` in `desktop/startup_phases.go`) requires both switches; a closed gate is a QUIET skip (Debug — an intentionally-off feature is not a failure), leaving the event tap unset and nothing listening. The section stays pure data: `backend/config/web_access.go` gains a doc-comment, no code — the loader, its fail-soft/fail-closed validity gates and every `web_access` RPC are untouched — and `internal/webaccess` never hears of the master gate (`New` still refuses only a disabled section or an invalid bind).

2. **Both switches live-follow mid-session; no restart anywhere.** The master switch rides a new desktop hook: `UpdateExperimentalFeatures` (`backend/frontend_api_config.go`) persists `experimental.enabled` FIRST, then invokes the hook carried through the `FrontendAPIConfig` seam (`OnExperimentalChanged` — the same construction channel as `AppCtx`/`QuitApp`) synchronously on the caller's goroutine — the toggle RPC returns only after the sidecar transition it caused has landed. `applyExperimentalWebAccess` (`desktop/app.go`, under `webAccessMu`): gate opened with the section's own switch on → mount (idempotent on a live sidecar); gate closed → bounded stop (`webAccessStopBudget`, the same budget `SetWebAccessEnabled` uses); every other combination is a no-op. The hook fires ONLY after a successful persist — the sidecar's lifecycle follows persisted operator intent, so a rejected disk write starts (or stops) nothing and leaves the mount decision to the next successful toggle or launch (a Warn, matching the toggle's pre-existing persist-failure honesty). The lock order stays one-directional (`configMu` → `webAccessMu`; desktop code never takes `configMu` — the zero-backend-edit constraint), and the hook installs once at startup inside `buildFrontendAPI` through that config seam — Init consumes it with the other seed fields, before the seed flag, so `seedAcquire` gives every toggle the happens-before edge and no install can race a toggle already in flight. The section's own switch (`SetWebAccessEnabled`) is unchanged — persist + hot start/stop under the same mutex — so under an open gate it keeps its exact pre-ADR behavior.

3. **The frontend hides the block with the same conjunction, keeping the ADR-090 web-transport rule.** The Settings → General Web Access block renders only while `experimentalEnabled && !isWebTransport()` — a render guard in `SettingsModal` around the border wrapper (the Session Statistics precedent), read reactively from `useExperimentalStore`, so flipping the master switch in Settings → Experimental hides/reveals the block within the same session without a reload, and the block disappears WITH its `border-t pt-4` wrapper instead of leaving an orphaned rule. Under a closed gate the inner toggle has no UI affordance; in the web transport the block stays hidden for the ADR-090 reason (the control RPCs are unreachable from a tab, so the section could only render "Status unavailable").

4. **The inner toggle is preserved as the section's own switch.** `web_access.enabled` keeps its meaning, its file location and its writer; the master gate adds a precondition, it does not replace the switch. This keeps the model honest in both directions: an open gate over a disabled section mounts nothing (pinned by test), and a closed gate never promotes — nor demotes — the section switch into a second master.

## Consequences

Positive:

- One switch now governs the app's three experimental surfaces (E2S, the embedded frontend, the web-access sidecar); a default machine serves no browser listener, and the surface can keep amending (TLS, a push stage) without every machine discovering it.
- The conjunction is enforced at the only two points where the app itself decides to mount (the startup mount, the gate hook) plus the one point where the UI affords the switch (the render guard) — the section, the sidecar package and the backend config layer stay gate-free code.
- Live-follow makes the gate cheap to open: `UpdateExperimentalFeatures` remains the single toggle RPC, and the mount lands in the same call — the way `SetWebAccessEnabled` always applied.

Negative:

- **Upgrade behavior for enabled configs is intentional**: every `config.yaml` that opted into web access before this ADR keeps its `web_access.enabled: true`, but the sidecar stops mounting at the first post-upgrade launch until the operator also turns `experimental.enabled` on (the master switch's default is off). A running listener disappears at that restart — the feature is now opt-in twice, and one silent service shutdown is the accepted price of the compound gate.
- The gate ages the scope wording again: ADR-044/ADR-056's "the switch still gates only the E2S execution mode" and ADR-068's two-surface enumeration are now stale; the live enumeration lives in `config.example.yaml`'s "Gated features today" list, the `ExperimentalConfig` doc-comments and AGENTS.md (all updated with this decision).
- ADR-068's frontend-only rule gets its first recorded exception: this gate reaches the backend (the mount), because a frontend-only gate would hide the block while the listener served. The exception is bounded by an argument the embedded model could not make: nothing persisted depends on the sidecar running (no stored config references the listener; the generated credential is written by the sidecar's own start and re-read by nothing else; a stopped sidecar invalidates no stored state) — so stopping it for real is safe, which is exactly what made a backend gate dangerous for `embedded`.
- The toggle RPC now carries a sidecar transition on its critical path (bounded by the stop budget; start failures are logged fail-soft and loud, never fatal). `GetWebAccessInfo`'s `enabled` (persisted intent) and `running` (live state) can legitimately disagree after a failed start — the fields already meant that; the gate adds no third state.

## Alternatives Considered

- **A frontend-only gate (the ADR-068 pattern).** Rejected: the block would vanish while `web_access.enabled: true` kept mounting a full-remote-control listener at every startup — the gate would hide the only surface that shows the feature is on. The embedded gate could be frontend-only because nothing persisted depended on its hidden backend; a serving listener IS the hidden backend.
- **Next-launch application** (gate checked only at startup, no live-follow). Rejected: the experimental switch is flipped in Settings, and "restart to apply" contradicts the hot-apply contract every other gated surface already honors (`SetWebAccessEnabled`, the embedded blocks, E2S's router rebuild); it would also leave `GetWebAccessInfo.Running` disagreeing with the revealed block until a restart.
- **Removing `web_access.enabled`** (master switch as the only gate). Rejected: it collapses two meanings into one key — the section's own opt-in (persisted beside bind/port/token, read by the sidecar package) and the app-wide development gate — re-creating exactly the two-switch coupling ADR-044 removed for Model Profiles, and turning the upgrade into a silent rewrite of every opted-in config file.
- **A dedicated per-feature opt-in key** (e.g. `web_access.acknowledge_experimental: true`). Rejected: a third switch to express "this is experimental" is one more stale boolean drifting against the other two; the master switch already carries exactly that meaning app-wide.
- **Gating at the loader** (reset the section while the gate is closed, like invalid binds). Rejected: the loader's fail-soft resets are keyed on VALIDITY — a valid, enabled section is operator intent that must survive config round-trips untouched, and the persisted credential must never be touched by anything but the token RPCs and the first-start mint; mangling the section under a closed gate would destroy the state the feature promises to preserve.
