# ADR-102: TLS for the web-access sidecar

## Status

Accepted — amended in place (2026-10-22, decision 4): the certificate pair is authored as two explicit paths validated as a unit at commit time, replacing the original one-cert-field-plus-derived-key design → Consolidates the branch-local former web-access TLS ADRs (then numbered 093/094/095) (the series was collapsed before the mainline merge): decision 2 states the final validity semantics (an unusable TLS turns the whole section off at load), decision 7 the plain-HTTP-only load exposure warning, decision 8 the live-following config-warning banner → Closes the deferred half of [ADR-101](./101-browser-web-access.md) decision 3 ("Transport security (TLS) is out of scope and gets its own future decision") and takes over the transport-warning semantics of its decision 12 → Amends the "plain HTTP stays the only transport" invariant and the cookie-`Secure` known limitation of [domains/web-access.md](../domains/web-access.md); the exposure classification (`IsLoopbackBind`) and the warn-only never-a-gate model stand unchanged

## Context

The web-access sidecar serves the desktop UI to a browser over plain HTTP: the session cookie omits `Secure` (recorded in code and in the domain spec as a known limitation "a TLS stage must flip it on"), and on a non-loopback bind the auth token is the *only* protection — traffic, including the login POST body, travels unencrypted. ADR-101 rejected shipping TLS together with the sidecar (certificate provisioning is a scope of its own) and explicitly left the seam open: bind address and credential handling had already arrived as mounted parameters, TLS termination was "the remaining seam".

Three forces shape the decision now. First, the operator need is real and bounded: serve `https://` from the sidecar without external tooling (no reverse proxy, no ACME client) — a self-signed certificate generated for the *currently pinned bind* covers the loopback and LAN-IP cases, and an operator holding a real certificate (or a proxy front) can point the config at it by hand. Second, the fail-soft/fail-closed doctrine of the config section gives an exact template for "TLS configured but broken": validity is ONE usability predicate — the structural rule plus whether the referenced pair actually loads — and a TLS the sidecar cannot serve must never stand in as the plaintext listener the operator did not ask for; a broken section still never keeps the app from starting, so the section heals to disabled instead. Third, the UX budget of the Settings block is already at its comfortable ceiling (one toggle, one URL field, one token field): the protocol must be a separate explicit switch, not a scheme parsed out of the address field, and the certificate needs two path fields plus one generate button — no more.

## Decision

The sidecar gains optional TLS termination, and the certificate it serves is generated by the app itself for the pinned bind:

1. **The protocol is its own switch: a `web_access.tls` subsection, externally toggled — never parsed out of the address field.** `tls.enabled` (default false) turns TLS on; `tls.cert`/`tls.key` carry PEM paths. The Settings address field keeps its host:port-only grammar: an explicit `http://` or `https://` scheme typed there is display-only — accepted and stripped (the field carries the address, never the transport, which is this toggle alone); any other scheme is refused with a message pointing at the HTTPS toggle. The toggle commits through its own control RPC `SetWebAccessTLS` on the desktop surface (ADR-101 decision 4) with the section's persist + hot-restart + rollback discipline. The rendered/copied browser URL switches to `https://` when TLS is on, so what the operator sees is always what the browser must open.

2. **An unusable TLS leaves no listener at all: usability is one predicate — structure + load — and a requested-but-unusable TLS never downgrades to plaintext.** `webAccessTLSPairError` (exported as `config.ValidateWebAccessTLSPair`) runs the structural rule (an enabled subsection needs both paths configured) and then loads the pair with `crypto/tls.LoadX509KeyPair` — the config layer READS the certificate files at load, the deliberate reversal of the original never-reads-the-files doctrine; a disabled subsection is usable by definition (inert, exactly like the whole section when `web_access.enabled` is off). At load, an unusable subsection — empty paths OR a pair that fails to load from disk (missing file, parse error, key/cert mismatch) — turns the WHOLE section off with one warning (`web_access.tls unusable (the sidecar stays disabled — a configured TLS is never downgraded to plain HTTP; fix the certificate pair or turn tls off, then enable web_access again): <reason>`), preserving bind, port, token and the subsection itself verbatim: the broken section never keeps the app from starting, there is no listener left to expose, and recovery needs nothing re-typed — fix the pair, flip the switch back on. The interactive boundaries fail closed on the same predicate: `SetWebAccessTLS` loads the pair BEFORE the no-op check or any persist (decision 4), and `SetWebAccessEnabled(true)` preflights it and refuses the flip with the load failure — nothing is mutated or persisted, so the toggle can never produce a persisted-on switch above a silently-down sidecar, and the operator learns the reason from the toggle's error instead of from a log line. The save gate stays structure-only: filesystem state must never brick an unrelated settings save. The mount remains the backstop for the one race the load path cannot see — `New` refuses a pair it cannot load (fail-closed, no plaintext downgrade; the start fails loudly with the error to the toggle caller and a hot-restart rolling back to the previously persisted state), a running sidecar keeps serving from its in-memory certificate, and a hot-restart that cannot reload the pair simply fails closed.

3. **The generated certificate is app-owned and address-scoped: one fixed pair in `~/.c0wrk`, regenerated for the current bind.** The Generate control — the second new desktop RPC, `GenerateWebAccessCertificate` — writes `~/.c0wrk/web-access.crt` + `~/.c0wrk/web-access.key` (paths through the `backend/config` path API): a self-signed ECDSA P-256 leaf, ServerAuth, 825-day validity, atomic write, key 0600 / cert 0644, with SANs covering the *currently pinned* bind — `{localhost, 127.0.0.1, ::1}` always, plus the bind's browser-facing host (a specific IP names itself). Generation persists the pair's paths into the section (minting-is-part-of-configuring, the token precedent) and hot-restarts a running sidecar onto the fresh certificate; it never flips `tls.enabled` and never touches operator-authored paths — clicking Generate overwrites only the standard pair it owns. **Amended in place (2026-10-25, the wildcard-bind SAN gap): a wildcard bind (`0.0.0.0`/`::`) adds the machine's non-loopback global unicast addresses to the IP SAN set** — deduplicated, IPv4-normalized, sorted, capped at 8, best-effort (an unreadable interface table degrades to the loopback-only set, never a failed Generate) — because the wildcard class serves every interface and the address a LAN browser actually opens is one of them; under the original wording that primary LAN use case was the one documented combination guaranteed to draw the `cert_status=mismatch` screen. An address beyond the cap still surfaces as a mismatch, with regeneration the documented fix.

4. **Both pair paths are explicit: two self-committing fields, validated as a unit at every commit.** The UI authors `tls.cert` AND `tls.key` — each field commits the full pair (its edited value plus the currently persisted counterpart) through `SetWebAccessTLS`, and every commit pre-loads the referenced pair BEFORE the no-op check or any persist, with the commit check's own two-bucket error split: a key that does not match its certificate is refused as a mismatch ("does not match"), every other load failure as an unreadable pair — deliberately NOT the `cert_status` vocabulary, which reserves `mismatch` for SAN non-coverage of the pinned bind and reports this same key-mismatch pair as `unreadable` (its classification loads the pair first, so any `LoadX509KeyPair` failure lands in unreadable); an enabled subsection with a cert but no key fails the structural rule ("tls.key is required"). A refusal lands on the field that was just edited with the draft preserved and nothing written, so an operator meets a broken pair at the commit that introduces it instead of at the next sidecar (re)start — the interactive boundary of decision 2's usability rule. After a pair has loaded once, an unchanged re-commit is a no-op that still validates: deleting a referenced file from disk fails the next commit even at unchanged values. Both fields MAY point at one file — a combined PEM carrying the certificate and the key in a single document is a valid pair. Generation re-seeds both fields from the post-mint re-read; `config.yaml` stays the escape hatch for layouts the two fields cannot express — the same hand-edit doctrine as static tokens, where tightening the UI must never lock an operator out of their own config.

5. **The cert/address mismatch is computed by the backend and surfaced as one warning.** `GetWebAccessInfo` gains additive fields (`tls_enabled`, `tls_cert`, `tls_key`, `cert_status`, `cert_detail`); whenever a cert path is configured, the leaf is read and checked against the pinned bind — SAN coverage of the browser-facing host, parseability, and expiry — producing `ok` / `mismatch` / `unreadable` / `expired`. The Settings block renders the detail as a warning row; changing the bind after the certificate was generated is the canonical mismatch trigger, and regenerating is the fix.

6. **TLS turns the documented limitations off, nothing else.** With TLS serving, the session cookie carries `Secure` (the KNOWN-LIMITATION comment's named resolution); on plain HTTP the cookie stays as today, so the HTTP behavior is byte-identical to pre-ADR. The same-origin WS check, the rate limiter, the denylist, the control-RPC placement (desktop.App only, ADR-101 decision 4) and the exposure warnings' surfaces are untouched (their scope is decisions 7–8's); `MinVersion` is pinned to TLS 1.2 (amendment, security-review fix round 2026-10-25: raised to TLS 1.3 — every mainstream browser has required 1.3 since ~2020–21, so the 1.2 surface was pure downgrade exposure; see [the domain spec](../domains/web-access.md)).

7. **The config-load network-exposure warning fires only while the effective transport is plain HTTP.** A TLS-encrypted non-loopback bind is a working, consciously configured setup: re-announcing it on every launch through the top "Configuration warning" banner — the one surface that reads as "the configuration is wrong — go fix it" — trains the user to dismiss the banner the real config errors (a broken section, a failed load) still need. The gate is `!IsLoopbackBind(bind) && !tls.enabled`, evaluated in `normalizeWebAccess` AFTER the fail-soft resets (including decision 2's usability rule), so the warning always describes the transport the sidecar will actually serve: a plain-HTTP non-loopback bind surfaces through all three channels (load warning → banner, section banner, start log); a TLS-encrypted one loads warning-free with the section and subsection preserved verbatim, keeping the two exposure surfaces that describe exposure without misusing the config-error channel. The message is single-shaped (`web_access: bind %q is not loopback — the listener is network-accessible, traffic is plain HTTP without TLS`, aligned with the sidecar start log's plain-HTTP wording) and `webAccessLoopbackWarning` loses its transport parameter; the sidecar start log keeps its two-variant transport-aware shape — a log line is not the config pipeline, and it stays transport-truthful for both tiers.

8. **The config-load-warning banner follows the live section, not the launch snapshot.** The banner renders `GetConfig().config_errors` — the channel the load pipeline fills once at startup (`normalizeWebAccess` → `LoadResult.LoadErrors` → `SetConfigLoadState`) — and a launch-frozen snapshot presented as live config state is a staleness bug: flipping the section to HTTPS must remove the plain-HTTP warning immediately, flipping back must restore it. **One pure text source:** `config.WebAccessLoadWarnings(section)` is the state-only counterpart of the `normalizeWebAccess` warning tail, which delegates to it, so load and runtime recompute cannot drift in text or condition; it computes ONLY the exposure warning and ONLY from state (enabled, `IsLoopbackBind`, `tls.enabled`) — the interactive writers preflight a TLS pair fail-closed (decision 2), so a runtime-mutated section can never carry an unusable TLS, and pair files that rot UNDER an already-persisted usable TLS stay owned by the section's `cert_status` banner (decision 5) and the mount backstop. A disabled section warns nothing — no listener, nothing to expose. **A surgical channel refresh, not a clear-all:** `FrontendAPILifecycle.RefreshWebAccessLoadWarnings` (the `SetConfigLoadState` precedent — on the Lifecycle, never the Wails RPC surface) drops every `web_access`-prefixed entry and appends the fresh set, under `configMu`; warnings from every other load-pipeline section (autonomy migration, MCP timeouts, …) survive untouched. **The three transport-affecting RPCs wire it in — outside `webAccessMu`.** `SetWebAccessEnabled`, `SetWebAccessConnection` and `SetWebAccessTLS` become lock-then-body wrappers (`…Locked` bodies keep the `webAccessMu` discipline) that call the refresh AFTER releasing the mutex: `UpdateExperimentalFeatures` holds `configMu` while invoking the ADR-101 decision-13 gate hook which takes `webAccessMu`, so acquiring `configMu` under `webAccessMu` would close an ABBA cycle. The refresh is idempotent, so it also runs after refusals and rollbacks and simply reflects whatever state the attempt left. The token RPCs and `GenerateWebAccessCertificate` deliberately do not refresh: neither the credential nor the pair's paths can move the section's warning state. The load pipeline remains the single STARTUP source, and the Settings → Web Access block fires `onConfigChanged` after every successful transport-affecting RPC so the "Configuration warning" banner re-reads the channel within one RPC round-trip.

## Consequences

Positive:

- The last ADR-101 stage seam closes: the sidecar now serves the same UI over an encrypted transport, and a non-loopback bind no longer means "token over plaintext". The loopback default keeps working exactly as before (TLS off = zero behavior change).
- The mismatch warning turns a previously silent breakage (cert generated for one address, bind later changed, browser hostname-verification failure with no hint why) into a visible, actionable row next to the control that fixes it.
- Pair breakage surfaces at the commit that introduces it: the commit-time pair validation (decision 4) reports an unreadable or mismatched pair at the edited field with the draft preserved, instead of at the next sidecar (re)start; the load-time usability rule and the mount's fail-closed race backstop are decision 2's.
- The one outcome a TLS configuration exists to prevent — a plaintext listener standing in for a broken encrypted one — is unreachable in every path: load, flip, mount (decision 2). The broken pair travels the config-error channel — the banner that says "go fix your configuration" carries the reason and the fix instead of a startup log nobody is tailing — and one rule, one predicate, one message shape cover both the structural and the file-level case, with the subsection surviving the healing so recovery is two operator actions with nothing re-typed.
- The top "Configuration warning" banner regains its meaning: what it shows is an unresolved configuration problem, not a persisted operator decision — an encrypted LAN listener no longer cries wolf on every launch (decision 7), and the banner states the truth about the current config: switching to HTTPS removes the plain-HTTP warning immediately, switching back (or re-binding onto a LAN address, or enabling the section) restores it, and disabling the section clears it — no restart, no modal reopen (decision 8). Load and runtime warnings share one text source, and unrelated load warnings survive every web-access transition.
- All new code sits in the existing seams — a `certgen.go` file in `internal/webaccess` (stdlib only, hygiene test untouched), one desktop file for the two control RPCs, additive config fields — so the removal path of the feature grows by deletion, not surgery.

Negative:

- A self-signed certificate still shows the browser's warning screen; the app does not touch the OS trust store (a deliberately rejected alternative — platform trust handling is a product decision of its own), so the operator accepts the warning once per browser or imports the cert manually.
- The sidecar can now be *down* where it previously would have been up-but-plaintext (TLS on, files broken): `running:false` with a loud error is the honest state, but an operator who ignored the Settings warning loses browser access at the next restart until they fix or disable TLS.
- A TLS commit is no longer a pure metadata write: every commit reads and parses the referenced pair synchronously on the control path (bounded local I/O), and a commit referencing a since-deleted file fails even at unchanged values.
- The 825-day validity and the fixed file pair mean a long-lived install silently crosses the expiry at some point — the `expired` status exists precisely to make that visible instead of discovered through a browser error.
- The new `SetWebAccessTLS`/`GenerateWebAccessCertificate` control RPCs and the `GetWebAccessInfo` payload extend the wire surface; the Wails bindings regenerate and stale frontend fixtures need the additive-default treatment.
- The load path performs filesystem I/O plus x509 parsing on every load while TLS is enabled (decision 2's usability predicate) — two small file reads, deterministic, but a real (if negligible) cost the pure-data section previously never paid; a section healed to disabled is indistinguishable, in the Settings toggle, from a manually disabled one — the distinction lives only in the load warning (mitigated by the message naming the subsection, the reason, and the fix).
- The desktop web-access layer now (indirectly) acquires `configMu` (decision 8) — safe only because it happens outside `webAccessMu`; the lock-order rule ("never configMu under webAccessMu") is a maintained invariant, not a structural guarantee. Web-access warnings are live-state while every other section's load warnings stay launch-frozen — an asymmetry that is correct (this is the only section with interactive transport flips) but must be remembered — and a refresh moves the section's entries to the END of the channel list (the list's order is not contractual, but the position within `config_errors` is not stable across a flip).
- The exposure-warning scope is now conditional (decision 7): an operator skimming only the "loads with exactly one exposure warning" invariant must read the plain-HTTP qualification to predict banner behavior (mitigated by the section banner remaining unconditional while enabled).

## Alternatives Considered

- **Scheme-in-the-address-field as the TLS switch** (`https://host:port` enables TLS) — rejected: the field already carries two values (host, port); a third overlapping the toggle's state invites divergence between what the field shows and what serves. The user chose the separate toggle.
- **Fail-soft HTTP fallback when the configured pair is unreadable** — rejected (user decision): it silently serves plaintext where the operator configured encryption, the exact "silently leaves an unsafe listener configured" outcome the section's doctrine forbids; the final semantics go further and treat the whole usability rule uniformly — an unusable subsection (structural OR file-level) heals the entire section to disabled (decision 2), the one shape that both refuses plaintext and keeps the app starting.
- **Trust-store integration** (mkcert-style local CA install) — rejected for this stage: per-platform trust tooling (macOS keychain, Windows cert store, NSS DBs) is a scope of its own with its own security review; the self-signed warning is the documented accepted consequence.
- **Operator-typed arbitrary generation path** (Generate writes wherever the field points) — rejected: the button would become an arbitrary-file-writer keyed on a text field, and could overwrite an operator-provided certificate; the fixed app-owned pair is idempotent to regenerate and safe to click.
- **ACME/Let's Encrypt in the sidecar** — rejected: external network dependencies and renewal lifecycle are far beyond the local-sidecar scope; operators needing trusted certs keep the reverse-proxy route ADR-101 already documented.
- **RSA keys for maximum compatibility** — rejected: ECDSA P-256 is universally supported by every browser this feature can reach and halves the key-handling surface; RSA remains available to hand-configured certificates.
- **One cert field plus a derived key** (the original decision 4, amended in place) — rejected after implementation: the derivation was the section's only implicit write (every other pin is persisted exactly as authored), it keyed an arbitrary derived path (the cert's own stem plus a `.key` suffix) on a text field — the same arbitrary-file-writer shape the Generate alternative above rejects — and it kept half the configured pair invisible to the operator; two explicit fields cost one input and retire the whole class.
- **One combined pair control** (a single picker committing cert and key together) — rejected: it cannot express the common split layout (separate cert and key files) without growing a second control, while two explicit fields already express the combined document — both paths at one PEM file — as a degenerate input of the general form.
- **Keep the load warning for every non-loopback bind (status quo)** — rejected (decision 7): it permanently occupies the config-error banner with a deliberate setup, dulling the surface actual misconfigurations need.
- **Also silence the sidecar start-log warning under TLS** — rejected (decision 7): the log is not the config-error channel; a transport-truthful Warn on every non-loopback start costs nothing and keeps the exposure visible in diagnostics where operators debug reachability.
- **Demote the load warning for plain HTTP too (drop the banner leg entirely)** — rejected (decision 7): token-over-plaintext on a LAN-reachable listener is exactly the "configuration deserves attention" case the banner exists for.
- **A `web_access.warned_on` ack flag to silence the banner after the first dismissal** — rejected (decision 7): persisted acknowledgment state adds a config field and UI flow to save one banner; the TLS gate already separates the deliberate case from the actionable one without new state.
- **Keep the subsection-alone reset at load (sidecar on plain HTTP)** — rejected (decision 2): it is precisely the plaintext fallback decision 2 removes; the listener would serve unencrypted exactly when the operator asked for encryption.
- **Keep `enabled: true` and gate the mount on a separate effective-state flag (`tlsBlocked`)** — rejected (decision 2): a second source of truth for "will the sidecar run" duplicates the master gate's job, leaks config-layer state into every gate reader, and renders in the UI as a switch that lies about the feature being on.
- **Make the save gate check the files (fail-closed at Save)** — rejected (decision 2): filesystem state would brick every unrelated settings save over a broken certificate; a settings write must never depend on the pair's on-disk mood.
- **Leave the pair check at mount only (status quo for the file-level shape)** — rejected (decision 2): an Error log is not an operator surface; the case would loop invisibly every launch with the banner — the one channel built for exactly this class of problem — silent.
- **Clear-all on every web-access write (the embedded/LLM save pattern)** — rejected (decision 8): it would wipe unrelated load warnings (autonomy migration, MCP timeouts) that no web-access action has any authority over.
- **Compute the web-access warnings fresh inside `GetConfig`** — rejected (decision 8): every other consumer of the channel would still see stale stored entries, and the banner would mix a live section view with a frozen rest-of-channel snapshot by accident of where the logic sits.
- **Refresh under `webAccessMu`** — rejected (decision 8): `configMu` under `webAccessMu` closes the ABBA cycle with `UpdateExperimentalFeatures` (which holds `configMu` while taking `webAccessMu` through the ADR-101 decision-13 hook).
- **Compose the banner text client-side from `GetWebAccessInfo`** — rejected (decision 8): a second warning text source in the frontend; the backend channel stays the single authority the load pipeline already feeds.
- **Fire `onConfigChanged` only when the warning actually changed** — rejected (decision 8): the frontend cannot know the recompute's outcome without a return channel; the recompute is state-only and idempotent, so unconditional is simpler and honest.
